Experiences, versions, publish

The start page is the dashboard: every experience here, where you worked last, and where an experience is made, exported, rolled back or deleted. Publishing happens from inside an experience.

A new experience

New experience goes step by step in the column:

  1. Start: pick Empty – one scene with a double page, nothing on it – or From an export – a file, a URL or a published version (below). Then Next.
  2. Name: a title and the address (the slug). The slug is proposed from the title – lower-case letters, digits and dashes – and the reader's address is shown in full under it: https://<installation>/<slug>/. The site keeps a few words for itself (editor, api, docs, scene, …) and every experience needs its own.
  3. Create: the experience is made and opens in the editor on its first scene.

The title can be changed later (the ⚙ next to the experience's name in the top bar). The address can't: once the experience is published, printed QR codes and shared links depend on it.

A new experience is a draft. Readers get nothing before the first Publish.

Importing an experience

Import brings an experience in as a new one – it is New experience → From an export. Three sources:

  • File: an export file (an experience's Export – ….osct.json, with its plugin code), or a game.config.json from your computer.
  • URL: a game.config.json, or a content base – an experience's folder on the CDN that holds latest.json, e.g. …/osct/staging/demo.
  • Published: the version of an experience this installation has published.

Assets at (for a bare game.config.json) is where the media paths resolve. No media is copied: the draft points at the files where they are.

Before anything is imported the column shows what comes in: the build, its date, the app and schema version and what it holds. Next goes on to the name – the title starts as the export's.

Managing an experience

Manage under a cover shows the experience's sheet in the column: title, author and reader address, and

  • Open: the experience in the editor.
  • Export: the draft as one file (<slug>-<build>.osct.json) – its content, its list of files and its plugin code. Import reads it back, here or on another installation. The media stay where they are; the file names them. Export before you replace or delete.
  • Replace…: replace the draft with an export, a URL or a published version. Below
  • Versions: every publish, and make live to go back to one. Below
  • Delete experience… at the end. Below

Replacing the draft

Replace… goes step by step: the source (file, URL or published), then Compare, then Replace the draft.

The comparison puts what comes in next to the draft: build, date, app and schema version, scenes, entries, targets, shared entities and plugin sources. Under it: whether the draft was edited since its last import – those edits would be lost – and whether the draft as it is now is published anywhere.

Only the draft changes. Readers keep the live version until you publish. Cancel goes back without a change.

Versions: going back to an older one

Every Publish is a version, and every version is kept. The sheet lists them newest first – when, where, who – and marks the one readers get now: ● live.

To roll back what readers get:

  1. Manage the experience and find the version in the list.
  2. Click make live in its row. It asks: Make the version of … live on staging again? Readers get it on their next start. The draft is not changed.
  3. Make live. The ● live mark moves to that version.
  • Readers get the older version the next time they start the app. Nothing is published anew, so it takes a moment, not minutes.
  • The draft stays as it is. Rolling back buys time; the mistake is still in the draft. Fix it there – or take the draft back too: Replace… › Published puts a published version into the draft, and History reverts single changes.
  • You can go forward again the same way: make live on the newer version.
  • An installation makes live for its own environment only: staging on staging, production on production.
  • An AI agent's connection cannot make a version live; that stays your button.

Deleting an experience

Delete experience… at the end of the sheet removes the experience from the editor for good. Nothing in the editor brings it back – no undo, no version.

  1. Export it first if you might need it again.
  2. Click Delete experience…. A red box says what goes: the scenes and entries, the plugin sources, the Library's records of its files, the history, the publish log.
  3. If the experience is live, the box says where. Read that line: see below.
  4. Type the experience's address (its slug, e.g. demo) into the field. Only then is Delete for good armed.
  5. Delete for good. Cancel or Esc leaves everything as it was.

What stays: the published builds and the uploaded files in the content store, and readers' progress. So where the experience is live, readers keep getting the published build – but no one can edit it, publish it or take it back from the editor any more.

To get an experience away from readers, deleting is the wrong tool. Publish a state you want them to have, or make an older version live.

Publishing

Publish is the cloud button in the top bar of an open experience. Next to it: draft only or live on ….

It opens one box in the middle of the page and asks first: Publish “…” to staging? with when it was last published. Publish starts it; Cancel, Esc or a click beside the box closes it. If a saved plugin source does not compile, the box says so in red and Publish stays off.

If the logic has errors or warnings, the box names how many and the first one; with errors the button says Publish anyway. They never block.

While it runs the box says Writing the build…, then Live for readers ✓ – readers have the new state from that moment – and counts the export archive. Keep the page open until it says Published, with how many files were new. It closes by itself after two seconds; Open reader opens the experience.

  • An installation publishes to its own environment only: a local machine to local, staging to staging, production to production. There is no choice.
  • Each experience has its own store. Publishing one never touches another.
  • No CDN connected means this server stores and serves the published content itself.
  • Publish carries the draft and every saved plugin source. Unsaved code stays behind.
  • A big experience takes a while – mostly the export archive, written after readers already have the build. Leaving the page while it runs asks first. If a publish is already running (another tab, after a reload), Publish shows that one.

Going back: make an older version live. Readers have it at once; then fix the draft and publish again.

Readers open every experience at its own address, /<slug>/ – /osct/, /demo/. Older codes and links without an experience still work: they open the installation's default experience, and the book's code its own.

AI connections

An AI agent (Claude Code, Claude Desktop, Codex CLI, OpenCode, Cursor) can work in the editor as you. It saves drafts and never publishes.

  • Connect an AI agent: pick the agent, press Create token & copy prompt, paste the prompt into the agent. It sets itself up.
  • Existing connections: each token with when it was last used and when it expires. Renew gives it another 182 days; Revoke stops it at once.

A token is shown once, so every agent gets its own. Details: MCP server.
