Plugin API

A plugin is one TypeScript file that exports register(api). It adds things the content can then use by name: components, node types, materials, textures, passes and looks.

Write and try plugins in the Code tab. This page describes plugin API 3.1 and how its parts fit together. Every member with its signature is in the Plugin API reference.

The shape

import type { PluginApi } from "osct-plugin-api";

  export const register = (api: PluginApi): void => {
    const p = api.p;
    api.registerComponent("spin", {
      description: "Turns the node around its own y axis.",
      params: {
        degreesPerSecond: p.number({ min: -360, max: 360, default: 30, unit: "°/s", label: "speed", description: "Speed." }),
      },
    }, ({ object, params }) => {
      let speed = params.degreesPerSecond;
      return {
        update: delta => { object.rotation.y += (speed * Math.PI / 180) * delta; },
        tune: next => { speed = next.degreesPerSecond; return true; },
      };
    });
  };

register runs once when the plugin loads. After a Run, spin is under add component in the Inspector, with a speed row.

Never import anything but types. three.js is api.three. A plugin that imports a module is refused.

What a plugin can register

FunctionAddsUse it for
registerComponent(type, spec, apply)a componentWhat a node does: spin, react to a tap, follow a variable.
registerLayer(type, spec, { glsl })a material layerA few lines of GLSL over a node's own picture: tint, scan lines, a pulse.
registerNodeType(type, spec, build)a node typeWhat a node is: you build the three.js object.
registerMaterial(type, spec, build)a materialHow a node looks: a whole three.js material, e.g. a ShaderMaterial.
registerTexture(type, spec, draw)a procedural textureA picture your code draws; every texture parameter can take it.
registerPass(type, spec, factory)a post-processing passAn effect over the whole rendered picture: film grain.
registerAppearance(type, spec, factory)a lookHow an entity appears and disappears.
registerCardLook(type, spec, factory)a card lookHow the card of a glossary entry flies from the page to the screen (API 4.1).

Type names are camelCase. Each type is then used in the content by its name, and the Inspector shows its rows.

Specs and parameters

A spec has a description, params, and optionally nodeTypes (the node types it fits). The Inspector builds its rows from it; the values your code gets are typed from it.

BuilderYour code gets
p.number({ min, max, default?, step?, unit?, slider? })number
p.integer({ min, max, … })a whole number
p.boolean({ default? })boolean
p.string({ default? })string
p.choice(["loop", "once"], { default? })"loop" | "once"
p.color({ default? })a hex string
p.texture()a three.js Texture or null: a Library picture or video, or a procedural texture
p.model()a model file's address; load it with api.loadModel
  • Every builder takes a description (the row's help) and an optional label (the row's words).
  • min and max are hard limits: the editor, the content check and the engine all enforce them. slider: [lo, hi] is only the range the control offers first.
  • You can also write the plain object: { kind: "number", default: 0.3, min: 0, max: 1, description: "…" }.

Hooks

A component's apply gets { node, params, object, placed, children, target, three, emit } and returns the hooks it needs. A node type's build gets { node, params, asset, target, three } and returns { object, …hooks }.

HookCalled
update(delta)every frame, with the seconds since the last
onFound(), onLost()the page is found, lost
onUnlocked()the page's first find
onTap()the reader taps the AR content
onAction(verb)a rule runs one of the spec's actions on this node
tune(params)the editor changed a value. Return true if you applied it in place, false to be built anew
onPause(), dispose()the scene pauses; the node goes. Free what you created

object is the node's own three.js object; placed the group that carries its placement; children the placement groups of its child nodes.

Events, variables, progress

PartWhat
api.eventson(name, payload => …) returns the unsubscribe; emit(name, payload?) sends a scene event. Core events (targetFound, targetLost, targetUnlocked, targetTapped, sceneChanged, arState, varChanged) can be listened to, never emitted.
api.varsset(name, value, scope?), get(name, scope?), on(name, (value, previous, scope) => …), all(scope). Scopes: scene (default), stage, session, experience. Values are strings, numbers or booleans; null deletes.
api.progressRead-only: unlocked(targetId), consulted(entryId), completion(sceneId?) (0–1), counts(sceneId?).
api.scenecurrent (id, label, group, surfaces, targets) and get(id).
api.log(…)To the console and the Code tab's log.
api.registerComponent("lamp", { description: "Lights when the door opened.", params: {} }, ({ object }) => {
    object.visible = api.vars.get("doorOpen") === true;
    const off = api.vars.on("doorOpen", value => { object.visible = value === true; });
    return { dispose: off };          // unsubscribe what a component subscribed
  });

These are the same events and variables the rules use.

Telling the Logic view what you do

A spec can declare how it takes part in the logic. The Logic panel draws these as ports on the node's box.

api.registerComponent("hum", {
    description: "Hums while the page is found.",
    params: { volume: p.number({ min: 0, max: 1, default: 0.6, description: "How loud." }) },
    actions: ["play", "pause"],                          // rule verbs it answers
    events: ["ended"],                                   // scene events it emits
    uses: { listens: ["doorOpened"], sets: ["hummed"] },   // what its code uses of the bus
  }, ({ emit }) => ({
    onAction: action => { /* "play" | "pause" */ },
    onTap: () => emit("ended"),
  }));
  • actions: any of play, pause, stop, show, hide. A rule's play: lamp then reaches onAction("play").
  • events: sent with the context's emit. An event the spec does not declare is not sent.
  • uses: listens, emits, reads, sets, by name.

Loaded files are shared by every node that uses them: clone what you change, never dispose them. They arrive after build returns: start with what you have and apply the file when its promise resolves.

A plugin of several files

A plugin is a folder: index.ts and, when it grows, more files next to it. TypeScript files are brought in by their name, shaders as text:

// index.ts
import type { PluginApi } from "osct-plugin-api";
import { bob } from "./bob";                // bob.ts
import TINT from "./tint.glsl";              // the file's text

export const register = (api: PluginApi): void => {
  api.registerLayer("seaTint", { description: "Tints towards the sea.", params: {} }, { glsl: TINT });
  bob(api);
};
  • File names: letters, digits, ., _, -, ending in .ts, .frag, .vert, .glsl or .wgsl. No folders.
  • Nothing else can be imported – no package (three.js is api.three), only the plugin's own files and import type.
  • At most 256 KB a file, 1 MB a plugin, 32 files. Every build puts the files together into one module for the reader.

Your own folder

To develop a plugin with your own editor, tests and repository, link a folder to it with the osct command (in the repository's scripts/; OSCT_API_URL is the instance's API, OSCT_EDITOR_TOKEN a token from the editor's experiences page, AI connections):

osct plugin link demo ./aquarium        # links the folder, pulls the plugin if it exists, adds the type files
osct plugin push ./aquarium --watch      # checks the types, sends the files – again on every change
osct plugin pull ./aquarium              # takes edits made in the editor back

A push is a save like the Code tab's: it is in History, the stage runs it, and the Code tab shows the plugin as linked. Anyone who may edit the experience can still change it there; the later save wins, and pull brings it home. The folder's own files (plugin-api.d.ts, shader-files.d.ts, tsconfig.json, a README) stay in the folder.

Layers, materials, passes

  • A layer's GLSL is the body of a function. It gets rgba (the pixel so far, linear RGB), uv, time, then the parameters in the spec's order (a number or boolean as float, a colour as vec3, a choice as int), and returns a vec4.
  • A material's build({ params, time, map, three }) returns a three.js material, or { material, update, tune, dispose }. End a fragment shader with #include <colorspace_fragment> and declare varying vec2 vUv so layers still work on it.
  • A pass's factory gets { params, three, shaderPass, size, pixelRatio } and returns a three.js pass. tDiffuse is the AR layer, premultiplied, in linear RGB.
  • A look's factory returns { duration, update(visible) }; visible runs 0 → 1 on reveal and found, 1 → 0 on lost. Use materials() for copies you may change; never change a mesh's own material.
  • A card look's factory gets the AR scene, the camera, the page's anchor, the pictures front, back, reveal and landing(width, fill), and returns { duration, update(t), dispose }; t runs 0 → 1, the entry opens when it is over. Add your card to scene, remove it in dispose; the engine frees the pictures. The experience picks it as appearance.card. Example: the demo's plugins/card.
api.registerLayer("tint", {
    description: "Tints the pixels towards one colour.",
    nodeTypes: ["video", "image"],
    params: {
      color: { kind: "color", default: "#f3cc94", description: "The tint." },
      opacity: { kind: "number", default: 0.3, min: 0, max: 1, description: "How much." },
    },
  }, { glsl: `return vec4(mix(rgba.rgb, color, opacity * rgba.a), rgba.a);` });

Feedback buffers

For pictures that need their own last frame (a fluid, ink): api.feedback({ width, height, fragment, uniforms?, channels?, type? }) runs your fragment shader once per frame into its own render target. Put its uniform into your material. api.shadertoy(source) turns a Shadertoy pass (mainImage) into such a fragment.

Where it runs

In the editor, plugins run in the editor's own page (since 5.0). A plugin can use the page's fetch with the session of the editor who has the experience open – read and change what that person may, the draft, the data, the game state. That is a risk: plugin code runs with the rights of whoever opens the experience. So the editor asks first – Run plugin code by …? – before it runs code someone else saved last; the answer is kept per experience and source version, and Don't run leaves those plugins off the stage. Your own last-saved code runs without asking. The reader app runs published plugins in its own page.

Shipping

  • Publish carries every saved plugin: its files type-checked, then put together in the browser like a Run.
  • The publish is refused on a type error (with the plugin, file and line), when a plugin does not build, or when a node uses a type no plugin registers.
  • Keep plugins small (a warning above 256 KB bundled). Everything runs on the reader's phone: up to three passes and one bloom per scene.
  • Unsubscribe in dispose what a component subscribed. Never emit a core event.
