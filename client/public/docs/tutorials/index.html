1 · Content workflow

The book's content lives in three places. Knowing which one you are looking at explains every button in the editor: sync, import, save and publish each move content from one place to the next.

1 · Content folderThe source: book.yaml, spreads, entries with their images and videos, and the layout/ rendered from the designed PDFs. It is not in the app's repository and the editor never writes into it.
2 · CDNVersions of the built content on bunny.net, one folder per build. latest.json names the one the reader loads. A version comes from a sync or from a publish.
3 · Editor databaseThe draft of a book on this instance: imported from a version, then edited – placements, AR nodes, uploads. Save writes here. Publish turns the draft into a new version.

Bringing a book onto an instance

Staging and production each have their own CDN folder and their own editor database. The first four steps happen once on the machine that holds the content folder; from step five on, everything happens in the browser.

  1. Render the layout from the PDFs once · content machine

    The editor's stage shows the book as designed when the folder carries layout/: every sheet as an image and every printed target's place in millimetres. Run it again only when the PDFs change.

    cd scripts
npm run layout -- --triggers "C:/path/All_Triggers.pdf" --preview "C:/path/OSCT_preview.pdf" --content ../content

  2. Build the content content machine

    scripts/.env names the folder (OSCT_CONTENT_DIR) and the storage access. The layout is not part of the build hash, so build with --force after rendering it.

    cd scripts
npm run build
npm run osct -- content build --force

  3. Sync to the CDN content machine

    The dry run says which version would be uploaded. The real run uploads the build as a new version – images, videos, layout – and switches latest.json to it.

    npm run osct -- content sync --env staging --dry-run
npm run osct -- content sync --env staging

  4. Check the reader browser

    The app loads the new version on its next start. Nothing else changes yet: the editor still has no book.

  5. Import the book editor

    Open the editor, sign in, Import a book…, source the CDN: the form shows the book and the build it found, and the button names them – Import 1 book: …. The current version becomes the draft: its spreads, entries and targets as rows in the database, every file still served from the CDN. With a layout on the CDN the spread cards show their sheets. The other ways in – a URL or a file – are in Bringing a book in.

  6. Edit and save editor

    Add the covers (+ cover, + back cover), place targets on the page, add AR nodes, upload files to the library. Save writes the draft. Readers see nothing of it yet.

  7. Publish editor

    Publish makes a new content version from the draft and switches latest.json – in the instance's own environment, and only there: the staging editor publishes to staging, the production editor to production. Next to the button the editor names it with its backend, staging · CDN or … · this server (no CDN connected – then the server stores and serves the content itself; back it up). A step in the page names the book and the build before anything is written. The reader picks it up on its next start. Every publish is kept as a version; the versions list shows who published what, and an older version can be made current again.

Things to know

Import replaces the draft. Importing again swaps the book's rows for the version imported – edits that were not published are gone (the change log stays). So the editor compares first: the build coming in against the build the draft is based on (date, app and schema version), and the edits made since. Only Replace the draft imports. Publish first, or cancel.

Sync and publish both make versions. A sync from the folder after editor work puts a version without the editor's changes on the CDN. Once the editor is where the book is edited, sync from the folder only when the YAML changed, and import again afterwards – placements saved in the draft survive that import only if they were carried back into the YAML first.

Nothing is deleted by itself. Old versions stay on the storage until osct content purge removes the ones provably out of use. A publish never touches the folder.

2 · Bringing a book in

A book gets into an instance's editor by an import. The import reads a game configuration – game.config.json, what the content build makes from the content folder – and turns it into the book's draft: spreads, entries, targets and AR nodes as rows in the database. One file is enough. The images, videos and models are not in it: they stay where they are, and the draft points at them.

An empty instance

A new instance has no book. The Books page says so, names the three ways in and links to this chapter. The form Import a book sits beside the list (under it on a phone). Under the books, AI connections makes a token for an AI agent – Claude, Codex, OpenCode, Cursor or any other MCP client – and Connect an AI agent shows the setup for each; the agent then saves drafts as you, and publishing stays your button.

Since 1.26.7 the form fills in addresses only on a developer's machine: on localhost it suggests the reader's dev server (http://localhost:5174/src/game.config.json, assets at http://localhost:5174). On staging or production nothing is filled in, and the CDN is selected – the instance's own published content is the usual way in.

Three ways in: the CDN, a URL, a file

The CDN – the instance's published content
The server reads its own content address (OSCT_CONTENT_BASE_URL; on staging https://buildingfictions.b-cdn.net/staging): latest.json names the current version, and the server fetches that version's game.config.json and files.json. Before anything is imported the form shows what it found: the content base, the current build (its id, when it was built and became current, the app and schema version) and the one book in it – title, id, spreads, entries, targets. The button names it: Import 1 book: The Demo Book (build 7457f0c…). The id is the configuration's book.id and names the book in this database, so an id that is already there replaces that book's draft – the form says so before you import. The assets base is set to the version's folder, and the version's files show in the Library.
URL – a game configuration, or a content folder
Either the address of a game.config.json – then fill in assets at yourself – or a content base: a folder with a latest.json, such as https://buildingfictions.b-cdn.net/demo. For a content base the form reads latest.json, takes <build>/game.config.json and fills in assets at with the version's folder. The browser fetches the file, so the address must allow it (the CDN does). Once you stop typing, the form shows the same preview as for the CDN.
File – a game configuration from this computer
A game.config.json on disk – a local build (client/src/game.config.json after npm run content) or one saved from the CDN. The file has no address of its own, so assets at must name where its media are.

Every way in takes the book id from the configuration's book.id, and every way in replaces the draft of a book with the same id – see Things to know. When such a draft is here, the preview says it first: A draft of “The Demo Book” (demo) is already here – importing replaces it., how many of its edits since its import are lost, and where it is live. The button then opens the version comparison, and only Replace the draft there imports. When the source can't be read – the CDN offline, no latest.json, or one that names no build – the form shows the error with the address and Try again.

The assets base

Every file in a configuration is named by a path that starts with /assets/content/, for example /assets/content/entries/key/key.glb. The assets base – the form's assets at – is the address put in front of those paths:

http://localhost:5174		http://localhost:5174/assets/content/entries/key/key.glb

Nothing is copied. The draft and every publish point at that address, so the media must stay reachable there. A version folder on the CDN never changes and is kept while it is current or recent (osct content purge removes only versions provably out of use), which makes it a safe assets base. The book page names it in its first line: 6 spreads · assets at …. Files uploaded in the editor are different: they live in the Library and are named by their own full address.

What is on the CDN

Each environment has its own folder on the CDN – staging, production, demo – and every content version is a folder of its own inside it. Everything under https://buildingfictions.b-cdn.net/ can be opened in a browser:

<env>/latest.json                 the current version
<env>/versions.json               every version, when it was current
<env>/<build>/game.config.json    that version's configuration
<env>/<build>/files.json          size and checksum of its files
<env>/<build>/assets/content/…    the files themselves

latest.json is the only file that is ever overwritten; a version's folder never changes.

latest.json says what readers load. The demo's, on 30 October:

{
  "build": "7a5254b5a4f6",
  "hash": "7a5254b5a4f6ff56150c5dcf360470284d9c4908762940a29f3c4c3e4f957633",
  "schema": "2.15",
  "version": "1.35.0",
  "activatedAt": "2026-10-30T01:32:57.404Z",
  "book": "demo"
}

build is the version's folder (the first twelve digits of the content checksum hash), schema the content schema it was built for, version the app version that built it (information only), book the book the environment serves. versions.json lists every version with uploadedAt, activatedAt and retiredAt – the current one has retiredAt: null. <build>/game.config.json shows what is in a version: the book's title, its spreads and entries.

To check an environment: open latest.json, find its build as the last entry of versions.json, and open <build>/game.config.json. With the storage key, the osct CLI shows the same in one line per version, and what the CDN serves:

cd scripts
npm run osct -- content status --env staging

Trust latest.json. On 30 October staging's latest.json named b6b0ebaabcfd, while its versions.json still listed only 6448aacb4ab7: that list is out of date, and osct content purge refuses to run until the two agree. Finding out why is part of #95.

When the media is missing

The draft imported, but the stage shows the pages without their entities, the spread cards are text instead of sheets, and the Library's previews stay grey. The configuration arrived; its files did not. The assets base is wrong, or the version it names is gone.

  1. Open the book page and read assets at in its first line.
  2. Put a path from the configuration behind it and open it in the browser, for example <assets base>/assets/content/book.yaml or an entry's image. A 404 means the files are not there.
  3. Find the right folder – usually the version's folder on the CDN, …/<env>/<build> – and import again with that assets at, or by the content base URL, which fills it in itself.

Importing again replaces the draft. When it already holds work that was not published, publish first (see Things to know).

3 · The demo book

The demo book is a sandbox, not the book. It uses every node type, every placement, a filter and every component the content model has. Seven plugins use every part of the plugin API, a node type of their own among them. And its spreads tell a small story: a key found on one page opens a door on another, a lamp lights when the door opened, a tally counts the pages found, a tap switches a scene.

Most files are the test fixture's small stand-ins – the "door" is a stack of boxes. The demo shows mechanics, not art. The key is a small brass key of its own with one animation clip.

Getting it in

The demo has its own folder on the CDN, buildingfictions.b-cdn.net/demo, apart from the book's staging and production.

  1. Import it into the editor editor

    Import a book…, source URL, and the base URL https://buildingfictions.b-cdn.net/demo. That is enough: the form reads latest.json and fills in assets at itself. Import, and The Demo Book appears next to the other books.

  2. Read it on a phone phone

    The staging reader takes a content address: https://osct.porschuetz.de/?content=https://buildingfictions.b-cdn.net/demo. It keeps it for the tab. The progress is kept apart from the book's. Production ignores the parameter.

  3. Publish the demo only on purpose editor

    One environment holds one book. A publish of the demo in the staging editor would replace the real book on staging, so the publish step names both books first. Read the demo on a phone with its content address instead (above), or publish it on a local editor, whose environment is local.

A walk through the spreads

Open a spread and the editor shows three things side by side: the tree on the left (pages, targets, nodes), the stage in the middle (the book on a desk, as the phone will see it) and the panel on the right (Inspector, Environment, Library, Code). The Inspector shows whatever is selected – the spread itself while nothing else is; the stage's toolbar holds how the stage looks.

The Library holds the files uploaded for a book – models, videos, images, audio – to use on any page. The demo's Library starts empty: its files come with the content. Upload one there, or with Upload… next to a node's file, and it is ready for every spread. Code files go there too: a shader (.glsl, .frag, .vert, .wgsl) that a plugin loads by its address, and a script (.ts, .js) that becomes one of the book's plugins. The filter code lists them with a read-only preview; Open in Code takes a script to the Code tab.

Cover

The cover is a spread of the format cover: the stage shows the closed book. The seal is an image. Its two layers come from plugins: tint colours it towards the book's gold, pulse makes it breathe.

1–2 · The key

The key is a model with three components. spin turns it around its own axis. animation says how the model's clip rattle plays: once, and never by itself. The behaviour holds one rule, made without code: on tap it plays rattle, sets the book variable hasKey – kept with the reader's progress – and sends the event keyRattled. To tap it without aiming, select the spread – its row at the top of the tree – and use tap in the Inspector's vars and events.

The tally is a group with a text. Its tally component draws "n of N pages found" and updates it on every new find, on any spread.

3–4 · The door

The door is a group with two children, named door and hint: the door model and a hint, "Tap the key on page 1". Its behaviour decides: when the page is found the hint shows; found with hasKey, the hint hides and the event openDoor goes out. The door component – plugin code – hears it: the door lifts and turns, the variable doorOpen is set and the event doorOpened goes out.

The lamp is a video with a chroma key and a pulse layer. Its lamp component keeps it hidden until doorOpen is set.

5–6 · The switch

The stage is a group of three children: an image, a video and a text. The scenes component shows one at a time. A tap on the entity shows the next – in the editor a click on the stage counts as a tap. The screen is a video standing upright, tinted, turned slowly by spin.

7–8 · The twins

twin-a and twin-b are two targets with the same entity: beacon, a model with a text and spin. The tree marks it as group · beacon. Change it once and both pages change.

Back cover

The colophon is a group with the text {{book.title}}, filled in from the book, and a tally of the whole book. It says "complete" when every page was found.

The story across the pages

The editor can play the story without a phone. Try it:

  1. Open 1–2 · The key. The Inspector shows the spread; open vars and events and press reset: a new game.
  2. Press tap → The key. The key rattles and hasKey appears as a book variable; the timeline shows the rule that ran.
  3. Press › to go to 3–4 · The door. The door lifts, doorOpen is set and the lamp lights.

The tree's eye switches a target off and on (lost, found again). Variables have scopes: spread lives while the spread is shown, stage while the scene exists, book is kept with the reader's progress. That is why hasKey survives the walk from page 1 to page 3.

Rules without code: behaviour

A behaviour is a component of rules. Select a node – the Inspector shows it – and press + behaviour under add component; then + rule. Each rule has three parts:

  • The event – found, lost, tap, unlocked (the page's first find), or event and a name: an event another rule or a plugin sends, like the door's openDoor.
  • + condition – a variable, = or ≠, and a value: true, false, a number or a text; empty means "not set". With two or more, choose all or any.
  • + action… – in order: play, pause or stop a clip of a model (the clips come from the model), show or hide a node (this node or a named child), set a variable with its scope, emit an event.

Every change runs on the stage at once – select the spread, press tap in its vars and events and watch. The timeline marks each rule that ran with a behaviour line: which rule, on which event, and what it did. A rule that is not finished yet – an empty name, no event – is listed in red and Save waits. A rule decides; what it cannot do, like moving the door over time, is plugin code that hears the rule's event.

How a component works

A component is a few lines of TypeScript in a plugin. The Code tab shows the book's plugins in a real code editor, with completion and type errors. Pick narrative: it holds door and lamp.

api.registerComponent("door", {
  description: "Opens the door (the first child) when it hears openDoor for its target: …",
  nodeTypes: ["group"],
  params: {
    lift:    { kind: "number", default: 0.35, min: 0, max: 2, step: 0.05, … },
    seconds: { kind: "number", default: 1.2, min: 0.1, max: 10, step: 0.1, … },
  },
}, ({ children, params, target }) => { … });

Each entry under params becomes a row in the Inspector: lift and seconds in the door's figure above. nodeTypes says where it may go – only on a group. Point at a row and the Info view at the bottom left shows its description. Change a value and the stage shows it.

Run tries the code on the stage at once: the plugin is replaced in place and the spread is built again. Save keeps the source with the book. Neither reaches readers. A plugin gets to the phone through the content build.

Pitfalls

Components can work against each other. The Inspector lets you put lamp on the door. It fits – lamp works on any node. But lamp hides its node until doorOpen is set, and the door is the one that sets it. Without the key, the door hides itself and the hint with it.

Back to the draft undoes every change since the last save. Nothing is stored until you press Save.

Post-processing

The spread's post-processing in the Inspector adds passes over the picture: + bloom, + vignette, + grade. Each has its rows, and changes show live. The stage shows them only in the rendered shading. The grade has a reach row: AR layer grades only the AR content, whole picture grades the desk too, as the reader grades the camera picture. The passes belong to the book, and a spread can have its own – see Post-processing: the book's and a spread's own.

Environment and sky

The Environment tab sets the world around the book: world (the built-in café or a glTF model), sky (the world's own or an image) and onion sky on or off. The onion sky needs a camera picture, so only the reader shows it. look up lifts the camera from the book towards the horizon, to see the world as a reader will. The twins' figure above shows it.

Once the book has an environment, its world is the stage's sky in every tab while the stage is rendered, and the stage is lit as the reader lights it – you see the world the reader will see. Around the book, where the reader sees the camera picture, the stage shows the studio picture. A book without one shows a studio picture (an HDRI) as sky and light.

How the stage looks is the toolbar's view group – the gear at its end, after grid & snap – stored on your device only: the hand shake, the origin every x / y counts from, the top of the desk under the book and the studio sky (the HDRI). Its tooltip names them all. The desk is always Egon Eiermann's steel frame; top switches between its screen-printed plywood and blue-grey linoleum on oak plywood. Only the top changes – the book, the targets and the camera stay where they are. With an environment the sky row names it – the environment's (world café) – and the HDRI waits below for a book without one.

Shading

The four spheres at the end of the toolbar change how the stage draws, as in Blender: wire (the entities as lines), solid (one grey), textured (the content's materials, no sky) and rendered (sky – the environment's world or the HDRI –, light and post-processing – the default). Wire shows what is hidden or stacked.

Grid and snap

The last button of the toolbar opens grid & snap: the grid and its step in mm, the green vertical axis that rises from the origin, and snap. With snap on, moving with the gizmo or dragging a printed image lands on the grid, the axes, other objects or the outlines of the prints and pages – a magenta line shows what it snapped to; rotating turns in steps of 15°, scaling in steps of 0.1. Choose what it snaps to and the steps in the same panel. Hold Shift while dragging to snap just this once (or not, when snap is on); with a finger, use the switch.

On a phone

The editor works on a phone too. The stage takes the top. The panel becomes a sheet at the bottom whose head is five icons – tree, Inspector, Environment, Library, Code. Tap the tree's icon and tap a row to select it: the Inspector sheet shows it, the spread's row as well as any other.

Drag to orbit, two fingers to pan, pinch to zoom. A double tap returns to the reader's view. ‹ and › at the stage's lower corners walk through the spreads. More in The editor on a phone.

To see the demo as a reader, open the staging reader with ?content= (see Getting it in) and point the camera at the printed pages.

The reference for every detail: the repository's fixtures/demo/ (the demo itself), docs/plugins.md (writing a plugin) and docs/editor.md (the editor).

4 · The editor's tools

The tools that came with versions 1.27 to 1.36, each shown on the demo book. None of these shots was saved: every change in them was taken back with Back to the draft. Nothing reaches the draft until you press Save, and nothing reaches readers until you Publish.

One selection: tree, stage and inspector

There is one selection, and it lives at a level: a target (the printed image), its entity (the root of its AR content) or a node inside it. Select in any of the three places and the other two follow:

  • The tree marks the selected row with its own grey and a bar at its start; the rows above it are lighter.
  • The stage outlines it in orange – a target around its printed image – and puts the gizmo on an entity or a node. The pick mode in the toolbar decides what a click picks: the entity, the node under the pointer, or the target.
  • The Inspector opens at that level. Its head is a breadcrumb, target › entity › group › node: a crumb steps up to that level, ▾ after the target picks another target of the spread.

In the tree, ↑ ↓ walk every row – the spread, the entries, the targets and the nodes –, ← → fold and unfold, and ← on a row that does not fold steps up a level.

Every row of the tree selects something, and a tap anywhere on the row always shows it: the row turns grey and the Inspector follows. The spread row – the book icon at the top – selects the spread: the Inspector shows its spread section – the title, the pages, the format, the post-processing in effect and the book's environment – then post-processing and vars and events; nothing stays selected on the stage, no outline, no gizmo. The spread is also what the Inspector shows when nothing else is selected: when the workspace opens, and after a click on the stage that picks nothing. An entry row selects the entry, also one without a target such as About the demo: the Inspector shows it as the reader reads it – category, title, access page, author and tags, the text in paragraphs, the image, a link's URL – and its target with select the target. An entry with a target has that target outlined on the stage. The Info view says for every row what its tap does.

Delete on an entry row removes nothing at once: it shows what goes with the entry and asks first, as Remove entry in the row's menu does.

Building a hierarchy

Drag a node row in the tree onto another row to make it that node's child – the row shows a frame – or between two rows to make it a sibling there – a line shows where. With a finger, drag the row by its icon. Keys do the same: Alt + ↑ ↓ move a node among its siblings, Tab indents it into the node above, Shift + Tab outdents it. A moved node keeps its placement values, now relative to its new parent.

+ node in the Inspector adds a node of a type – group, model, video, image, text, light, and the book's own node types – and add as says where: next to it (the same parent, right after the selected node; the default for a model, video or image) or inside it (its last child). Next to the root, both go into a new group. Every node has a name: the tree shows it, with the type as the icon.

The Library as the picker

Every file field – a target's printed image, a node's file, a new node's file, the new target's files, the environment's world and sky – has Library… next to Upload…. Library… opens the Library in place of the panel: its filter starts at the kind being picked, a click on a card takes that file for this one field and returns, an upload that fits is taken at once, and cancel or Esc returns without one. The panel underneath keeps its values. The target image filter lists the pictures printed in the book, apart from the other images.

A new target

+ target at the end of the tree opens the form for a new target on the spread. It keeps two choices apart: what appears on the page – none, model, video, image, text, group or light, with its file – and the entry category, where the reader's consultation menu lists the entry. The category follows what appears – a video makes a video entry, everything else a glossary term – until you set it by hand. Below them, where it is printed: the surface, x and y, and the width in millimetres; the stage shows a ghost of the image there, with handles to drag.

Adding and removing spreads

The book page has + double page in its first line: a new, empty double page after the last one, before the back cover. Every card has a menu – a right click, a long press or the menu key – with Open, Add a double page after and Remove. A new double page takes the two pages after the spread before it, and every later page is numbered on by two – the later spreads, their entries and their targets' printed pages move with them.

Remove takes the spread out with everything on it, and asks first. The card shows what goes – Removes spread 5–6 with 3 entries, 2 targets, 2 entities. –, that the pages after it are numbered back, which shared entities stay because other targets use them, and that the Library files are kept; an option, off at first, also deletes the files used only there. Nothing is removed until you press Remove spread 5–6 in that confirmation; Keep leaves everything as it was. The spread the book opens on cannot be removed: its Remove is disabled, and the Info view says why.

Post-processing: the book's and a spread's own

The passes in the spread's post-processing (the Inspector, the spread selected) belong to the book: edited once, every spread without a list of its own shows them. The section's head names the level in words: post-processing · the whole book while the spread on the stage uses the book's list, post-processing · only this spread while it has its own. It starts closed, and its head still says the level.

The line under the head says what editing changes. With the book's list it counts the spreads: changes all 5 spreads that use the book's. own for this spread at its end gives this spread an override that starts as a copy of the book's; the line then reads overrides the book's for this spread, and back to the book's drops the override again. Save says what it saves: Save for the whole book, Save for this spread, or Save for the book and this spread when both lists changed.

The book's plugins can bring passes of their own. add pass offers them in a row per plugin, under its name: the demo's grain plugin has + filmGrain, which the twins already use, and a plugin you Run in the Code tab shows up at once. A plugin's pass has its own rows – here strength, size, speed, reach and a pattern picture from the Library – and the arrows move any pass earlier or later in the chain.

Tap, variables and the timeline

The spread's vars and events in the Inspector plays a book's story by hand, without a phone. It is closed until you open it by its head.

  • tap has a button for each printed target of the spread. It taps the target's AR content as a reader's tap would, without aiming at it: the entity's onTap, the animation component's plays on: tap and the event targetTapped. A target that is not found, or has no AR content, is greyed out.
  • vars lists the plugins' and the rules' variables, each with its scope and type and a control for its value – false / true, a number or a text – and × to delete it. set adds one: a camelCase name, the scope (spread, stage, session or book), the type and the value. Both write through the plugin API, so the plugins and rules react as if one of them had set it: set hasKey to true on the door's spread, switch the door off and on with the tree's eye, and it opens without a visit to page 1. reset starts a new game.
  • events is the timeline, newest first: the time since the spread opened, the event and its payload. The last 100 are kept; clear empties it.

Nothing here is saved to the draft: the variables live while the spread's workspace is open, as a reader's progress lives on the phone.

Code everywhere: a node type, a material, a texture

A book's plugins can go where the big engines let code in. A component says what a node does, a node type what it is, a material how it looks – the whole material, or a layer of GLSL over its own –, a procedural texture what it shows, a pass what happens to the whole picture. Every one has a spec, so the Inspector shows its rows without any panel code.

The demo's Aquarium on page 2 uses three at once: the node type aquarium builds the glass tank and its fish, the material water is a shader with waves on its surface and a tint that deepens with the angle, the floor's light is the procedural texture caustics. Select Tank in the tree: under node type · aquarium are the tank's rows – the floor light is a texture row, a list of none, the plugins' procedural textures and the Library's pictures and videos – and under material · water the water's rows, with remove. A node without a plugin material shows material its own, a list of the materials that fit it.

The tank is also a small shader study: a plastic toy fish dips into the water and rises again, and a tap pushes it in once. Where it cuts the surface it pushes the water aside, rings run outward, bounce off the glass and settle, and the light on the floor gathers under them – the surface is simulated on a grid of cells, and the water shader and the floor read it. Its rows are at the end of the tank's: dipping toy (fish, ball or none), loop period, dip depth, simulation (off: the water's old static waves), grid (32, 64 or 96 cells – finer rings, more work), damping and splash.

Where the browser has WebGPU, the water is a real fluid instead: thousands of particles simulated and drawn on the GPU (Splash, by Masaya Matsuoka), seen through the tank's faces from the stage's camera, and the toy pushes them aside as it dips. The row WebGPU says what this browser has – WebGPU ok runs the fluid while it is on, no WebGPU keeps the rings above – and particles, render scale and fluid colour follow it.

A plugin can also keep a picture of its own on the GPU that remembers its last frame – a feedback buffer: the engine runs a fragment shader into it every frame, before the scene. The demo's Ink painting on page 6 is a framed canvas whose ink never stops flowing: a fluid from Shadertoy (XlsBDf by trapcode, CC BY-NC-SA 3.0), pasted in nearly unchanged. Tap it and the ink swirls where you tapped; select Painting and the Inspector shows its resolution (256 or 512 – the phone's cost), pen speed and ink dissipation.

make it code, in the head of any node, turns the node into a node type of the book's own – Unreal's Create Blueprint class from a component. The editor writes a plugin into the Code tab whose registerNodeType reproduces the node: its type's builder as a readable starting point (here a model: a copy of its scene, its clips playing), its values as the spec's parameters. It saves the plugin, runs it and switches the node to the new type, where it was. From then on it is your code: change the build, Run, Save. make code beside the material row does the same for the node's look, as a registerMaterial. The draft changes only when you press Save in the Inspector.

The page is the zero plane

Whatever stands on the page has its lowest point on the paper. A model whose origin is its middle sinks half into the page unless its position lifts it by its lower half; the content build reads every model's bounding box, follows it through the placements above it and warns when it floats or sinks, naming the position that stands it on the page. The demo's beacon was such a model.

Words as labels

Every row in the Inspector is labelled in words: a parameter's label from its spec (key color, compare by, soft edge), or else its name split into words (degreesPerSecond → degrees per second). The Info view names the row by its words and by the name the content uses – key color · color – so a row can still be found in the YAML or a plugin's code. A plugin gives its own parameters a label the same way.

The editor on a phone

With a finger every control is 44 px high (2.75rem), the tree's rows, chevrons and eyes too. The panel is a sheet at the bottom whose head is five tab icons sharing the width – tree, Inspector, Environment, Library, Code. Tap the open tab to close the sheet down to its head; tap another to open it. Drag the head to any height, from the tab row alone to almost the whole screen; let go and it snaps to closed, a third, half or almost full, and a flick carries it on. While it is dragged, the stage keeps its size and the sheet slides over it. A double tap on the grip restores half.

‹ and › sit at the stage's lower corners and walk through the spreads. The book's name in the top bar leads back to the spreads. The toolbar is one row of four buttons, each opening its menu: gizmo, pick, shading, grid & snap.

The editor on a tablet

On a tablet in portrait – a window under 1024 px – the tree starts collapsed to its bar, so the panel keeps its 25rem and the stage the rest. Open the tree with › at the left; the choice is kept on the device. A panel too narrow for the tab words shows the tabs as icons, so its head stays one line. With the tree open as well, the panel narrows, and its position, rotation and scale rows put their label above the X, Y, Z fields.

The column edges can be dragged on a tablet too: the panel from 16rem to 70% of the window, the tree from 10rem to 40%. A double tap on an edge restores its width.
