1 · Content workflow

The book's content lives in three places. Knowing which one you are looking at explains every button in the editor: sync, import, save and publish each move content from one place to the next.

1 · Content folderThe source: book.yaml, spreads, entries with their images and videos, and the layout/ rendered from the designed PDFs. It is not in the app's repository and the editor never writes into it.
2 · CDNVersions of the built content on bunny.net, one folder per build. latest.json names the one the reader loads. A version comes from a sync or from a publish.
3 · Editor databaseThe draft of a book on this instance: imported from a version, then edited – placements, AR nodes, uploads. Save writes here. Publish turns the draft into a new version.

Bringing a book onto an instance

Staging and production each have their own CDN folder and their own editor database. The first four steps happen once on the machine that holds the content folder; from step five on, everything happens in the browser.

  1. Render the layout from the PDFs once · content machine

    The editor's stage shows the book as designed when the folder carries layout/: every sheet as an image and every printed target's place in millimetres. Run it again only when the PDFs change.

    cd scripts
npm run layout -- --triggers "C:/path/All_Triggers.pdf" --preview "C:/path/OSCT_preview.pdf" --content ../content

  2. Build the content content machine

    scripts/.env names the folder (OSCT_CONTENT_DIR) and the storage access. The layout is not part of the build hash, so build with --force after rendering it.

    cd scripts
npm run build
npm run osct -- content build --force

  3. Sync to the CDN content machine

    The dry run says which version would be uploaded. The real run uploads the build as a new version – images, videos, layout – and switches latest.json to it.

    npm run osct -- content sync --env staging --dry-run
npm run osct -- content sync --env staging

  4. Check the reader browser

    The app loads the new version on its next start. Nothing else changes yet: the editor still has no book.

  5. Import the book editor

    Open the editor, sign in, Import a book…, source the CDN, Import. The current version becomes the draft: its spreads, entries and targets as rows in the database, every file still served from the CDN. With a layout on the CDN the spread cards show their sheets.

  6. Edit and save editor

    Add the covers (+ cover, + back cover), place targets on the page, add AR nodes, upload files to the library. Save writes the draft. Readers see nothing of it yet.

  7. Publish editor

    Publish with the environment makes a new content version from the draft and switches latest.json. The reader picks it up on its next start. Every publish is kept as a version; the versions list shows who published what, and an older version can be made current again.

Things to know

Import replaces the draft. Importing again swaps the book's rows for the version imported – edits that were not published are gone (the change log stays). Publish first, or do not import again.

Sync and publish both make versions. A sync from the folder after editor work puts a version without the editor's changes on the CDN. Once the editor is where the book is edited, sync from the folder only when the YAML changed, and import again afterwards – placements saved in the draft survive that import only if they were carried back into the YAML first.

Nothing is deleted by itself. Old versions stay on the storage until osct content purge removes the ones provably out of use. A publish never touches the folder.

2 · The demo book

The demo book is a sandbox, not the book. It uses every node type, every placement, a filter and every component the content model has. Six plugins use every part of the plugin API. And its spreads tell a small story: a key found on one page opens a door on another, a lamp lights when the door opened, a tally counts the pages found, a tap switches a scene.

The files are the test fixture's small stand-ins. The "key" is a dragon, the "door" is a stack of boxes. The demo shows mechanics, not art.

Getting it in

The demo has its own folder on the CDN, buildingfictions.b-cdn.net/demo, apart from the book's staging and production.

  1. Import it into the editor editor

    Import a book…, source URL, and the base URL https://buildingfictions.b-cdn.net/demo. That is enough: the form reads latest.json and fills in assets at itself. Import, and The Demo Book appears next to the other books.

  2. Read it on a phone phone

    The staging reader takes a content address: https://osct.porschuetz.de/?content=https://buildingfictions.b-cdn.net/demo. It keeps it for the tab. The progress is kept apart from the book's. Production ignores the parameter.

  3. Publish only to local editor

    One environment holds one book. A publish of the demo to staging would replace the real book there, so the editor asks first and names both books. Publish the demo to local, or to staging only on purpose.

A walk through the spreads

Open a spread and the editor shows three things side by side: the tree on the left (pages, targets, nodes), the stage in the middle (the book on a desk, as the phone will see it) and the panel on the right (Stage, Entity, Environment, Library, Code).

The Library holds the files uploaded for a book – models, videos, images, audio – to use on any page. The demo's Library starts empty: its files come with the content. Upload one there, or with Upload… next to a node's file, and it is ready for every spread.

Cover

The cover is a spread of the format cover: the stage shows the closed book. The seal is an image. Its two layers come from plugins: tint colours it towards the book's gold, pulse makes it breathe.

1–2 · The key

The key is a model with three components. spin turns it around its own axis. key sets the book variable hasKey on the first find – it is kept with the reader's progress – and a tap sends the event keyRattled. animation would play a clip on a tap; the stand-in model has none, so it waits for a real one.

The tally is a group with a text. Its tally component draws "n of N pages found" and updates it on every new find, on any spread.

3–4 · The door

The door is a group with two children: the door model and a hint, "Find the key on page 1". When the page is found, the door component reads hasKey. With the key, the door lifts and turns, the variable doorOpen is set and the event doorOpened goes out. Without it, the hint shows.

The lamp is a video with a chroma key and a pulse layer. Its lamp component keeps it hidden until doorOpen is set.

5–6 · The switch

The stage is a group of three children: an image, a video and a text. The scenes component shows one at a time. A tap on the entity shows the next – in the editor a click on the stage counts as a tap. The screen is a video standing upright, tinted, turned slowly by spin.

7–8 · The twins

twin-a and twin-b are two targets with the same entity: beacon, a model with a text and spin. The tree marks it as group · beacon. Change it once and both pages change.

Back cover

The colophon is a group with the text {{book.title}}, filled in from the book, and a tally of the whole book. It says "complete" when every page was found.

The story across the pages

The editor can play the story without a phone. Try it:

  1. Open 1–2 · The key. In the Stage tab, open vars and events and press reset: a new game.
  2. Right-click the stage and choose Replay the first find. hasKey appears as a book variable.
  3. Press › to go to 3–4 · The door. The door lifts, doorOpen is set and the lamp lights.

The tree's eye switches a target off and on (lost, found again). Variables have scopes: spread lives while the spread is shown, stage while the scene exists, book is kept with the reader's progress. That is why hasKey survives the walk from page 1 to page 3.

How a component works

A component is a few lines of TypeScript in a plugin. The Code tab shows the book's plugins in a real code editor, with completion and type errors. Pick narrative: it holds key, door and lamp.

api.registerComponent("door", {
  description: "Opens when the page is found and the reader has the key; …",
  nodeTypes: ["group"],
  params: {
    lift:    { kind: "number", default: 0.35, min: 0, max: 2, step: 0.05, … },
    seconds: { kind: "number", default: 1.2, min: 0.1, max: 10, step: 0.1, … },
  },
}, ({ children, params }) => { … });

Each entry under params becomes a row in the Entity panel: lift and seconds in the door's figure above. nodeTypes says where it may go – only on a group. Point at a row and the Info view at the bottom left shows its description. Change a value and the stage shows it.

Run tries the code on the stage at once: the plugin is replaced in place and the spread is built again. Save keeps the source with the book. Neither reaches readers. A plugin gets to the phone through the content build.

Pitfalls

Components can work against each other. The Entity panel lets you put lamp on the door. It fits – lamp works on any node. But lamp hides its node until doorOpen is set, and the door is the one that sets it. Without the key, the door hides itself and the hint with it.

Back to the draft undoes every change since the last save. Nothing is stored until you press Save.

Post-processing

The Stage tab's post-processing adds passes over the picture: + bloom, + vignette, + grade. Each has its rows, and changes show live. The stage shows them only in the rendered shading. The grade has a reach row: AR layer grades only the AR content, whole picture grades the desk too, as the reader grades the camera picture. Save writes the passes to the spread.

Environment and sky

The Environment tab sets the world around the book: world (the built-in café or a glTF model), sky (the world's own or an image) and onion sky on or off. The onion sky needs a camera picture, so only the reader shows it. look up lifts the camera from the book towards the horizon, to see the world as a reader will. The twins' figure above shows it.

The Stage tab has two more settings, stored on your device only: the desk under the book and the studio sky that lights the stage.

Shading

The four spheres at the end of the toolbar change how the stage draws, as in Blender: wire (the entities as lines), solid (one grey), textured (the content's materials, no sky) and rendered (sky, light and post-processing – the default). Wire shows what is hidden or stacked.

On a phone

The editor works on a phone too. The stage takes the top. The panel becomes a sheet at the bottom: drag its handle, and the tabs turn into icons – tree, Stage, Entity, Environment, Library, Code.

Drag to orbit, two fingers to pan, pinch to zoom. A double tap returns to the reader's view. ‹ and › walk through the spreads.

To see the demo as a reader, open the staging reader with ?content= (see Getting it in) and point the camera at the printed pages.
