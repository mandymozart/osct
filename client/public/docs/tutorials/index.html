Content workflow

The book's content lives in three places. Knowing which one you are looking at explains every button in the editor: sync, import, save and publish each move content from one place to the next.

1 · Content folderThe source: book.yaml, spreads, entries with their images and videos, and the layout/ rendered from the designed PDFs. It is not in the app's repository and the editor never writes into it.
2 · CDNVersions of the built content on bunny.net, one folder per build. latest.json names the one the reader loads. A version comes from a sync or from a publish.
3 · Editor databaseThe draft of a book on this instance: imported from a version, then edited – placements, AR nodes, uploads. Save writes here. Publish turns the draft into a new version.

Bringing a book onto an instance

Staging and production each have their own CDN folder and their own editor database. The first four steps happen once on the machine that holds the content folder; from step five on, everything happens in the browser.

  1. Render the layout from the PDFs once · content machine

    The editor's stage shows the book as designed when the folder carries layout/: every sheet as an image and every printed target's place in millimetres. Run it again only when the PDFs change.

    cd scripts
npm run layout -- --triggers "C:/path/All_Triggers.pdf" --preview "C:/path/OSCT_preview.pdf" --content ../content

  2. Build the content content machine

    scripts/.env names the folder (OSCT_CONTENT_DIR) and the storage access. The layout is not part of the build hash, so build with --force after rendering it.

    cd scripts
npm run build
npm run osct -- content build --force

  3. Sync to the CDN content machine

    The dry run says which version would be uploaded. The real run uploads the build as a new version – images, videos, layout – and switches latest.json to it.

    npm run osct -- content sync --env staging --dry-run
npm run osct -- content sync --env staging

  4. Check the reader browser

    The app loads the new version on its next start. Nothing else changes yet: the editor still has no book.

  5. Import the book editor

    Open the editor, sign in, Import a book…, source the CDN, Import. The current version becomes the draft: its spreads, entries and targets as rows in the database, every file still served from the CDN. With a layout on the CDN the spread cards show their sheets.

  6. Edit and save editor

    Add the covers (+ cover, + back cover), place targets on the page, add AR nodes, upload files to the library. Save writes the draft. Readers see nothing of it yet.

  7. Publish editor

    Publish with the environment makes a new content version from the draft and switches latest.json. The reader picks it up on its next start. Every publish is kept as a version; the versions list shows who published what, and an older version can be made current again.

Things to know

Import replaces the draft. Importing again swaps the book's rows for the version imported – edits that were not published are gone (the change log stays). Publish first, or do not import again.

Sync and publish both make versions. A sync from the folder after editor work puts a version without the editor's changes on the CDN. Once the editor is where the book is edited, sync from the folder only when the YAML changed, and import again afterwards – placements saved in the draft survive that import only if they were carried back into the YAML first.

Nothing is deleted by itself. Old versions stay on the storage until osct content purge removes the ones provably out of use. A publish never touches the folder.
