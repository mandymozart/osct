# An experience in a git repository – the fundamental integration

Tilman, 2026-11-23: *"connecting github for external storing of experiences? … how would we auto deploy new commits –
like in netlify when connecting a repo"* · *"i think we need a two directional workflow. so the editor can also commit,
as does any other git user who has access to the repo."* · on the first drafts (merging per field, previews, a developer

## 1. The idea in one paragraph

An experience can be connected to one folder of one GitHub repository. No page of its own: the setup is a **Repository** section of the book's
Manage sheet (experiences page, under Versions); the state and the commit are one item in the editor's top bar next to
*live on …*, which opens a dialog like Publish's. **Out**: *Commit*
writes the experience's export – the folder `osct content export` writes today – as one commit, authored by the person.
**In**: a push to the branch runs one workflow in the repository that builds the folder with the existing CLI and sends
it to the instance, which brings it into the draft and publishes to staging. **Both changed**: no merging – a person
picks a side, git keeps the other in its history. Production stays the editor's Publish.

## 2. What is reused, what is new

Reused as it is: the export format (`experience.yaml`, `scenes/`, `entries/`, `entities/`, `plugins/<id>/index.ts`,
`credits.yaml`, `export.json` – media stay in the Library, named by URL and sha256 as in the #322 archive), `osct content
build`, `POST …/import` with its version comparison (`confirm-import`), Publish to staging, the change log.

New:
1. **Repository section** in the Manage sheet (`ExperienceSheet.svelte`), per experience: repository URL, branch, folder, access token (fine-grained, *Contents: read and
   write* on that repository; stored on the server, never shown again).
2. **Sync state**: the commit the draft was last in sync with, and the draft's hash then. From it the top bar's item (shown only when a
   repository is connected): *In sync* · *n saves not committed* · *Repository is ahead* – the same words in the sheet.
3. **Commit**: the export of the draft written as one commit through GitHub's API (a tree and a commit – no git binary on
   the server); the workflow file is added by the first commit.
4. **The repository as a fourth source** of the import (next to file, URL, published): *Compare…* in the editor's
   *Repository is ahead* dialog and *Replace…* in the sheet show the existing comparison with it.
5. **`osct push --dir … --publish staging`**: the CLI sends the built configuration and the plugin sources; the server
   imports **without the comparison** only when the draft is unchanged since the synced commit, else refuses (409, the run
   fails with the reason and the editor shows *Repository is ahead*); then publishes to staging.
6. **A token kind** for the repository: one experience, may bring in and publish to staging, nothing else.

Not committed: `game.config.json` (a build output). No new manifest, no lock file – the export is the format.

## 3. Out of the fundamental version (later, if ever)

Merging per field, incoming commits without a push workflow (webhooks), branches and pull requests from the editor, preview
builds, a unified history of saves and commits, a developer kit (`npm create …`, `osct dev`), shared plugins by tag,
Forgejo/Gitea and plain SSH. The first drafts of these are in git history (the first version of `git-sync.html`).

## 4. Decisions for Tilman (recommendation first)

1. **Host**: GitHub only for the first version (recommended) · GitHub and Forgejo together.
2. **Both changed**: a person picks a side (recommended) · the editor refuses to commit until the repository's version is taken.
3. **Auto-deploy target**: a push publishes to staging (recommended) · a push only brings into the draft, publishing stays a
   person's step.
4. **First user**: the demo (`fixtures/demo` moves to its own repository folder and `demo.yml` goes) (recommended) · the book.

## 5. Pitfalls

- The export must be deterministic (key order, formatting) – else every commit rewrites every file. Test: export → build →
  export gives the same bytes.
- Schema MAJOR cuts (no backward compatibility until Tokyo): a repository on an older schema is migrated by one commit from
  the editor after the instance's migration, never silently on push.
- The token lives on the instance, per experience; the repository's `OSCT_TOKEN` secret is the editor's – two secrets, one
  each way.
