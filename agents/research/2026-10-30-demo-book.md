# The demo book: a sandbox that uses everything, and the smallest plugin API it needs (#80, decided 2026-10-30)

Tilman (2026-10-29, after #66): "können wir lokal ein Beispiel erzeugen, das einmal versucht, alle Möglichkeiten, die
der Editor gerade kann, zu simulieren – auch mit diversen Game-Narrativen und Interaktionen, mit der Buch-API, also
auch Progress etc., und mit Inter-Spread-Interaktionen? … call it demo … das würde ich, wenn wir fertig sind, dann
auch im Staging ausliefern, dass wir am Beispiel lernen können, was möglich ist." This note decides where the demo
lives, what it shows, what today's model carries, and the smallest additions to the plugin API (1.0 → **1.1**) that
make the narratives run. The concept behind it: `2026-10-28-entity-components.md` ("Events: book logic apart from
scene logic, and the scopes", "Studio C"), the plugin API: `2026-10-29-code-in-the-editor.md`.

## Where it lives: `fixtures/demo/`

A second content folder next to the test fixture, built with `OSCT_CONTENT_DIR=fixtures/demo`. The fixture
(`fixtures/content/`) stays the tests' content – every test and CI job builds it, and it must keep the shape the
tests expect; the demo is free to change with every idea. Both are small (the demo reuses the fixture's models,
videos and target images; no book content – RULES #8). The demo is marked by `DEMO.md` (copied into the build like
`FIXTURE.md`): `osct content sync` refuses a demo build for any environment but **`demo`**, so it can never replace the
book's current version on `staging` or `production`. A scripts test builds it like the fixture test does.

## What it shows, spread by spread (book id `demo`)

| Spread | Pages | Targets and what happens |
|---|---|---|
| **cover** (`format: cover`) | 0 | *seal* – an image with the `tint` and `pulse` layers, its printed place on the surface `front` |
| **the-key** | 1–2 | *key* – a model that spins (`spin`); the first find sets the book variable `hasKey` (the `key` component, `onUnlocked`); a tap emits the scene event `keyRattled`. *tally* – a group whose `tally` component draws a line of text with `api.three`: "n of N pages found" from `api.progress`, updated on every `targetUnlocked` |
| **the-door** | 3–4 | *door* – a group: the door model (a child) and a hint text (a child). The `door` component reads `hasKey` when the page is found: with the key the door opens (the child lifts and turns, the spread variable `doorOpen` is set, the event `doorOpened` fires), without it the hint shows. *lamp* – a chroma-keyed video with a `pulse` layer that stays dark until `doorOpen` (the `lamp` component, `api.vars.on`); when the door opens on the same stage the lamp lights |
| **the-switch** | 5–6 | *stage* – a group of three children (an image, a video, a text): the `scenes` component shows one and a tap switches to the next. *screen* – a video standing upright, tinted, with the `animation` component's cousin: `spin` with a slow speed |
| **the-twins** | 7–8 | *twin-a* and *twin-b* – the shared entity `beacon` (a model with a text child and `spin`), `ref` from two targets |
| **back** (`format: back`) | 9 | *colophon* – a group with `{{book.title}}` as text and the `tally` of the whole book: "complete" when every page was found |

Every node type (group, model, video, image, text), placements (rotation, position, scale, non-uniform), a filter
(`chromaKey`), a shared entity, `print` on every target (the stage lays the pages out without a book layout), the
covers as spreads of a format, entries of every category, two onboarding steps. The **plugins**
(`fixtures/demo/plugins/<id>/index.ts`): `tint` (the fixture's layer), `pulse` (a layer that breathes with `time`),
`spin` (a component), `scenes` (a tap switches the visible child), `narrative` (the components `key`, `door`, `lamp`
– the book logic), `tally` (text from the progress). Together they use every hook and every part of the API.

The `animation` component is in the content model and the Entity panel, but none of the fixture's small models has an
animation clip (checked: tree, dragon, boxes, chest), and a model with one would be a new asset of some hundred KB.
So the demo places the component on the *key* with `playOn: tap` – it does nothing until a model with clips replaces
the stand-in; the note says so in the entry's body. A tiny animated GLB (made in Blender like the desks) is a
follow-up when someone has one.

## What today's model carries, and what had to be added

Carried by the model of 1.11.0: the node tree, placements, filters, components, layers, shared entities, `print`,
the formats, the plugins' type check and bundle, the editor's Run. **Not carried** (the gaps are the point of the
issue): anything that crosses a node – a find on one page that changes another page, a text that knows the progress,
a tap that changes the whole entity, a lamp that listens. The concept names what is missing: events with two owners,
variables with scopes, the book API. Built here, as small as the demo needs (`engine/src/scene/plugin-runtime.ts`,
`plugins.ts`; **plugin API 1.1**, the content schema stays 2.4 – nothing in the content contract changed):

- **`api.events`** – one bus. *Core events* belong to the engine and are read-only for plugins: `targetFound`,
  `targetLost`, `targetUnlocked` (the first find – the app tells the engine through `celebrate`, so progress stays the
  app's), `targetTapped`, `spreadChanged`, `sceneState` (running / paused / stopped), `varChanged`. A plugin that
  emits one gets an error. *Scene events* are free: `api.events.emit("doorOpened", { … })`, any name that is not a
  core event; every plugin on the stage hears it. `on` returns the unsubscribe; a plugin's listeners go when the plugin
  is uninstalled (the editor's Run replaces them), so a forgotten unsubscribe cannot pile up.
- **`api.vars`** – `get(name, scope?)`, `set(name, value, scope = "spread")`, `on(name, listener)`, `all(scope)`.
  Values are JSON scalars (string, number, boolean; `null` deletes). The scopes of the concept: **`spread`** lives
  while the spread is the current one (cleared on `spreadChanged`), **`stage`** while the scene exists (cleared when
  it is torn down), **`session`** per app start, **`book`** persisted with the reader's progress. A `get` without a
  scope looks outward – spread, stage, session, book – and the innermost definition wins, as the concept says. The
  `node` scope of the concept is not an API: a component's own closure *is* the node's state, and a node's components
  share the three.js object (`object.userData`) if they must.
- **`api.progress`** – read-only: `unlocked(targetId)`, `consulted(entryId)`, `completion(spreadId?)` (0–1, the
  whole book without an id), `counts(spreadId?)` (`{ unlocked, targets }`). The engine gets it from the app through
  `ArSceneOptions.progress` (a `ProgressReader`): the reader passes an adapter over its history manager, the editor
  its simulation (RULES #32 – never the store). Without one, nothing is unlocked and `book` variables live in memory.
- **`api.spread`** – `current` (the spread as the engine knows it: id, title, pages, format, targets) and `get(id)`.
- **The component context** grew `children` (the children's placement groups, in content order – the `door` and
  `scenes` components work on them) and the hook **`onUnlocked`** next to `onFound` (the first find of the target).

**`book` variables are persisted** in the reader's progress record as an optional `variables` map. The record's
format is the app MAJOR (RULES #10); an optional field within format 1 has a precedent (`onboarded`, read as absent
in older records), so this is a MINOR: `readFormat1` keeps the scalars it finds, `mergeProgress` keeps this device's
values and fills gaps from the other record. Variables that no spread sets any more stay in the record like unknown
ids.

What stays out, with the reason: **bubbling scopes for events** (node → spread → stage – one flat bus serves the
demo; the stage *is* where plugins meet), **declared variables** with `type` / `write` lists (the plugin is the
declaration for now; a `variables:` block in the content comes when behaviours without code exist), **the
`behaviour` component** (events → actions without code – the next step after this demo shows what authors reach
for), **`global` scope** (the server, a privacy decision), **`api.registerNodeType`** (#77), **spread-level nodes
without a target** (the `tally` sits on a target; an anchor for the spread's scene is still open – PLAN 15.2c).

## How the demo reaches a phone on staging

Three ways were on the table: a content base URL per book, a second Kamal destination, a book switch in the reader.
**Recommended and built: the demo gets its own environment `demo` on the storage zone, and the reader takes a content
base URL on debug builds.**

- The workflow **`.github/workflows/demo.yml`** builds `fixtures/demo` and runs `osct content sync --env demo` with
  the `staging` environment's storage credentials (by hand, and on a push to `develop` that touches the demo, the
  engine, the shared contract or the content build). The CDN then serves `https://buildingfictions.b-cdn.net/demo/`
  with `latest.json` and the immutable version folders, like the book's `staging/` – no second destination, no second
  image, nothing of the demo in the book's folders.
- **The reader** on a debug build (staging has `VITE_DEBUG`) honours `?content=<base url>` and keeps it for the tab
  (`sessionStorage`): `https://osct.porschuetz.de/?content=https://buildingfictions.b-cdn.net/demo` opens the demo
  book in the staging reader on a phone, progress apart from the book's (the record is per book id). Production builds
  ignore the parameter.
- **The editor** on staging imports the demo with *Import a book… → URL*: the base URL `…/demo` is enough now – the
  form reads `latest.json`, takes the version's `game.config.json` and sets *assets at* to the version folder. The
  stage shows it, the Code tab shows its plugins (the compiled ones carry their `index.ts`).

Open, as issues: **a publish is per environment, not per book** – the store's `latest.json` of `staging` names one
book; an editor who publishes `demo` to `staging` would replace the book's current version once staging publishes to
the CDN (`CONTENT_STORE=bunny`). Until the store learns a book segment (`<env>/<book>/…`), the demo on staging is
published to `demo` by the workflow only, and the editor's Publish of the demo stays `local`. The second open item:
the editor cannot run the content build, so a plugin edited in the editor reaches the demo's readers through this
repository and the workflow (#78 closes that gap for every book).

## What the editor simulates, and what it cannot yet

The Stage panel's **found** chips and **replay** drive the whole narrative: switch the *key* off and on (found again,
`onFound`), replay (the first find again, `onUnlocked` – `hasKey` set), walk with ‹ › to *the door* (`spreadChanged`,
the spread variables cleared, the door reads the book variable), switch the *lamp* off and on. The Stage panel got a
**narrative** block: the variables with their scopes and the last events, and *reset* clears every variable and locks
every target again – the demo starts over without leaving the page. The Code tab shows the six plugins; Run replaces
one in place.

Not simulated yet: a reader's **consulted** entries (the editor has no entry view; `consulted()` is always false on
the stage), **a reader's stored progress** (the editor's progress lives as long as the workspace is open – leaving the
spread list and coming back starts a new game), **two spreads on one stage** (grow loading holds neighbours' targets
in the reader; the mock tracker reports the current spread only, so "the lamp lights while the door opens on the
other page" is seen in the reader, in the editor it lights when the lamp's page is found with `doorOpen` set – a
`stage` variable survives the switch where a `spread` variable does not, which is what the demo shows), and **the
reader's UI** around it (the unlock notice, the entry list). A **tap** is simulated: a click on an entity on the
stage reaches the engine's hit test like a reader's tap (`onTap`, `targetTapped`) – the switch's scenes change on a
click. Checked in the browser (2026-10-30, the screenshots in the session's notes): the key's unlock sets `hasKey`,
› to the door opens it and lights the lamp, the Stage panel shows the variables and the events, the Entity panel the
plugins' rows, the Code tab the six plugins.

Open: a *tap* button per target in the Stage panel (without aiming at the entity), a timeline of events with time
stamps, the variables editable from the panel (a `set` by hand to test a branch).

## Decided alone, to review

The plugin API version 1.1 (MINOR – additions only), the shape of `api.vars` (positional `set(name, value, scope)`
with `spread` as the default scope – the most used one in the concept's examples), the flat event bus, the
`variables` map in the progress record as a MINOR, the environment `demo` instead of a per-book store, `?content=` on
debug builds only.
